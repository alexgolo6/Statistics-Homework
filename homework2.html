Homework 2: From wallet seed to Ethereum address

Hashing, key derivation and cryptographic primitives.

1. The pipeline

  1. Random entropy (128 to 256 bits): the only random step.
  2. BIP-39: entropy becomes a mnemonic of 12 to 24 words, then a 512-bit seed.
  3. BIP-32: the seed becomes a master key, then a tree of child keys.
  4. BIP-44: a path such as m/44'/60'/0'/0/0 picks one key in the tree: the private key k.
  5. secp256k1: the public key is Q = k·G.
  6. Keccak-256: hash of Q; the last 20 bytes are the address.
  7. EIP-55: some letters of the address are capitalised as a checksum.
Just to give a concrete example, here is the standard public test phrase from the Hardhat dev tool (obviously, never use this for real funds!):
test test test test test test test test test test test junk
If we run this through the standard Ethereum derivation path (m/44'/60'/0'/0/0), it spits out this specific address:
0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266 (Raw lower-case format)
0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266 (EIP-55 format: notice the capital letters acting as a checksum)

3. The six pieces

BIP-39 (2013)

Words are easier to copy than random bits. 128 bits plus 4 checksum bits make 132 bits, which is 12 words of 11 bits each (the list has 2048 = 211 words). The seed is made with PBKDF2-HMAC-SHA512 (2048 rounds), optionally with a passphrase.

BIP-32 (2012)

One seed produces a whole tree of keys, so only one backup is needed. The master key comes from HMAC-SHA512 of the seed. Each child key is computed from its parent and an index.

BIP-44 (2014)

A standard path layout so that all wallets find the same accounts: m / purpose' / coin_type' / account' / change / address_index. For Ethereum the purpose is 44 and the coin type is 60.

secp256k1

The curve y² = x³ + 7 over a 256-bit prime. The public key is Q = k·G, the same operation as in Homework 1 with big numbers. It is also used for the signatures (ECDSA) that authorise transactions.

Keccak-256 (2015)

The address is the last 20 bytes of the Keccak-256 hash of the public key (64 bytes, x and y).

EIP-55 (2016)

Take the lower-case address, hash that text with Keccak-256, and capitalise each letter whose matching hash digit is 8 or more. The address stays valid for old software, and a wallet can detect most typos.

4. Why not one single algorithm?

Each step has a different goal, and one algorithm cannot do them all:

  • BIP-39 / 32 / 44: key management and derivation (one backup, same accounts in every wallet).
  • secp256k1: the private/public key relationship and digital signatures.
  • Keccak-256: hashing, a short fixed-size identifier from the public key.
  • EIP-55: error detection for typos.

Also, if one primitive turns out to be weak, the others are not automatically broken.

5. Timeline

  • 1977: RSA. One of the first public-key schemes, by Rivest, Shamir and Adleman. Its security rests on the difficulty of factoring large numbers.
  • 2001: SHA-2 / SHA-512. NIST standardises the SHA-2 hash family. SHA-512 is later used inside the PBKDF2 and HMAC steps of BIP-39 and BIP-32.
  • 2012: BIP-32. Hierarchical deterministic wallets: one seed gives a whole tree of keys. In the same year Keccak wins the NIST SHA-3 competition.
  • 2013: BIP-39. Mnemonic words as a human-friendly way to write down the seed.
  • 2014: BIP-44. Standard derivation paths for several accounts and several cryptocurrencies.
  • 2015: SHA-3 and Ethereum. NIST standardises SHA-3 (based on Keccak, but with a changed padding). Ethereum launches, using the original Keccak-256.
  • 2016: EIP-55. Mixed-case checksum for Ethereum addresses, to catch typing mistakes.

The technologies belong to different layers. RSA (1977) is a public-key scheme, and secp256k1 later brought elliptic-curve public-key cryptography to wallets. SHA-2 (2001) and later Keccak / SHA-3 are hash functions. The BIPs (2012 to 2014) are wallet standards built on top of these primitives. Ethereum (2015) chose Keccak-256 and secp256k1, and EIP-55 (2016) added a checksum on top of the existing address format.

First the basic primitives, then the need to manage many keys, to remember them, to make wallets compatible, and finally to avoid typos.

6. SHA-2 / SHA-512 versus Keccak / SHA-3

Both are hash function families. SHA-2 uses the Merkle-Damgard design, while Keccak uses a different one, called a sponge. NIST picked Keccak for SHA-3 as a backup with a different structure, not because SHA-2 was broken.

Ethereum adopted Keccak before the standard was finished. In the final SHA3-256, NIST changed the padding, so the outputs differ: Keccak-256 is not the same as SHA3-256. For the empty string:

SHA3-256a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a

7. Statistical properties

  • Entropy: the first random bits must be uniform. 2048 = 211, so uniform bits give uniformly chosen words.
  • Hashes (SHA-512, HMAC, Keccak): outputs look random and show the avalanche effect (about half of the bits change if one input bit changes).
  • Keys: k is uniform over a huge range. Q looks random but has a structure: (k+1)G = kG + G. It has no avalanche (see Homework 1).
  • Address: 160 bits, so two random addresses collide only after about 280 tries.
  • EIP-55: each letter's case is one check bit, about 15 per address, so a random typo is detected almost always.

8. Wallet experiment

To see how this works in practice, I played around with a test wallet on MetaMask. When I set it up, it gave me the standard 12-word recovery phrase (which is BIP-39 in action). After that, I added a second account, and the app generated a brand new address using the exact same phrase—a perfect example of the BIP-44 derivation path. I even tried importing those same 12 words into a different wallet app, and it loaded the exact same addresses, proving the whole deterministic derivation thing is real. Finally, I tried to mess up an address by changing just one capital letter, and the wallet immediately threw an 'invalid checksum' error, so EIP-55 definitely does its job catching typos!
