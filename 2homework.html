3. Elliptic-curve scheme on secp256k1

This follows the Part 1 idea (public key Q = k·G), using the secp256k1 curve (y² = x³ + 7 modulo a 256-bit prime) and JavaScript BigInt values. The private key is restricted to a small range (1 to 16384, about 14 bits) so that the attack in section 6 is feasible. This is a simplified, educational ElGamal-style scheme, not a complete or production-ready ECIES implementation. It works on letters as follows:

  1. Public setup: the curve and the base point G are known to everybody.
  2. Receiver's keys: the receiver picks a secret integer k and publishes the point Q = kG.
  3. Sender encrypts: the sender picks a fresh random scalar r in the valid range 1 to n−1 and computes C1 = rG and the shared point S = rQ.
  4. Keystream: the x coordinate of S is hashed with SHA-256 to get one number for every letter, and each letter is shifted by its own number (modulo the alphabet size).
  5. The sender transmits C1 and the ciphertext.
  6. Receiver decrypts: the receiver computes S = k·C1. This is the same point, because k·r·G = r·k·G = r·Q. The keystream is rebuilt and every letter is shifted back.

Role of the keys: Q is public, so anyone can encrypt for the receiver, but the receiver's private key k is needed to rebuild S and decrypt. The value r is a fresh, one-time random scalar and should not be reused. This toy scheme also has no message authentication, so it should not be used to protect real data.

4. Statistical comparison

To get more letters I encrypted my sample text (about four copies of the same passage) with both methods and counted the letters. I use two numbers. The index of coincidence (IC) is the probability that two letters taken at random from the text are the same: about 0.07 for real language and 1/n for random letters (n = alphabet size). The chi-squared value measures the distance from the uniform distribution; for random letters it should be close to n − 1.

Similarities. In my implementation, both schemes change letters using numbers modulo the alphabet size, and decryption reverses those changes. In both cases, the receiver needs the correct shift or keystream to recover the message.

Differences. Caesar uses the same shift for the whole message, so the language's frequency pattern is preserved, although the letter labels change. The ECC toy scheme uses a keystream that changes from one letter to the next, so the frequency pattern is less directly visible in the ciphertext. The key space also differs: Caesar has only a small number of shifts, while the ECC key space depends on the allowed range for the private key. Caesar requires both sides to know the same shift; with public-key ECC, the sender can use the receiver's public key without learning the private key.

5. Statistical attack on the Caesar cipher

The algorithm I implemented is simple:

  1. Use the reference letter frequencies for the selected language (section 1).
  2. Count the letters of the ciphertext.
  3. Test every possible shift. For each candidate, compare the resulting letter counts with the reference frequencies using the chi-squared score.
  4. Select the shift with the smallest score as the most likely key.

6. Attack on the restricted private key

The private key k is restricted to the values 1 through 16384. The attacker knows Q and G, so the attack computes G, 2G, 3G, and so on until a point matches Q. When it finds a match, the corresponding number is the private key k. The attacker can then calculate S = k·C1 and decrypt the message in the same way as the receiver.

Comparison with the statistical attack

The statistical attack on Caesar works on the ciphertext: it uses the fact that letter frequencies survive the shift. The ECC attack works on the key space: it does not need to analyse the message, but it does need the public key Q and the fact that there are very few possible private keys. The public key is available by design.

Why it is not feasible on a properly configured scheme

A properly configured secp256k1 private key is chosen from a range with about 2256 possibilities (more precisely, from the valid non-zero scalars below the curve order). Even at 109 trials per second, checking a space of this size would take roughly 1060 years, far longer than the age of the universe. The same exhaustive-search idea is practical here only because the toy version has 16,384 possible keys. This comparison concerns brute-force search; it does not mean that every possible ECC implementation is automatically secure against every kind of attack.

Other attacks and where the weaknesses come from

From the restricted key space: an attacker could precompute all points k·G for k up to 16,384 and look up the public key in that table. More advanced methods, such as baby-step giant-step or Pollard's rho, can reduce the work to roughly the square root of the number of candidates (about 128 steps in this toy range, at a high level). For a properly sized 256-bit elliptic-curve group, generic attacks of this type still require roughly 2128 operations, which is not practical.

From the design of my toy scheme (not from the key size):

  • If I used S only as a single shift for the whole message, the ciphertext would be a Caesar cipher and the attack of section 5 would break it without touching the curve. This is why I use one number per letter.
  • If the sender reuses r with the same public key, the keystream repeats, and the difference of two ciphertexts reveals the difference between the two messages modulo the alphabet size.
  • There is no authentication: an attacker can modify the ciphertext and the receiver would decrypt a changed message without noticing.

7. Conclusion

For me, the main lesson is that the two attacks exploit different weaknesses. The Caesar cipher preserves the language's letter-frequency patterns, which makes statistical analysis possible. The ECC toy scheme is not broken by this same simple attack, but its private key can be recovered because the allowed range is very small. With a properly configured ECC scheme and a sufficiently large private-key space, this direct search would not be practical. The experiment also shows why the design and implementation of an encryption scheme matter, not just the size of its keys.
